Theory: Function-Based Views vs Class-Based Views

1. What is a Django View?

In Django's Model-View-Template (MVT) architectural pattern, a View is a Python callable (a function or a class) that accepts a web request and returns a web response. The response can be the HTML contents of a Web page, a redirect, a 404 error, an XML document, or an image.

Django views encapsulate the application logic necessary to process incoming data, interact with models (the database layer), and select the appropriate template or HTTP status code for the client.

2. Function-Based Views (FBVs)

Function-Based Views are standard Python functions that take an HttpRequest object as their first parameter (typically named request) and return an HttpResponse object.

HTTP method handling in FBVs is done imperatively using conditional statements like if request.method == 'POST':.

Example: Simple Function-Based View
from django.shortcuts import render
from django.http import HttpResponse

def article_list(request):
    if request.method == 'GET':
        # Retrieve and render articles
        articles = ["Django Overview", "Views Architecture", "Routing Guide"]
        return render(request, 'articles.html', {'articles': articles})
    elif request.method == 'POST':
        # Process submitted article
        return HttpResponse("Article created successfully", status=201)

3. Class-Based Views (CBVs)

Class-Based Views provide an object-oriented approach to implementing views in Django. Instead of procedural branching with conditional statements, HTTP methods are mapped directly to corresponding instance methods (such as get(), post(), put(), and delete()).

CBVs inherit from the base django.views.View class or generic view classes. The class is hooked into Django's URLconf via the class method as_view().

Example: Simple Class-Based View
from django.views import View
from django.shortcuts import render
from django.http import HttpResponse

class ArticleListView(View):
    def get(self, request):
        articles = ["Django Overview", "Views Architecture", "Routing Guide"]
        return render(request, 'articles.html', {'articles': articles})

    def post(self, request):
        return HttpResponse("Article created successfully", status=201)

4. Request-Response Lifecycle in Django

When an HTTP request reaches the Django server, the lifecycle proceeds through the following sequential steps:

  1. WSGI/ASGI Handler: Web server receives the raw request and initializes the WSGIRequest / HttpRequest object.
  2. Middleware Processing: Request middleware (security, sessions, CSRF, authentication) execute in order.
  3. URL Resolver: Django consults the root URLconf and matches the requested URL pattern to resolve the target view.
  4. View Execution:
    • For FBVs: The target function is called directly with request and matched URL parameters.
    • For CBVs: The as_view() closure instantiates the view class, sets self.request, calls dispatch(), and routes execution to get(), post(), etc.
  5. Response Generation: An HttpResponse instance is returned, processed by response middleware, and returned to the client browser.

5. FBV vs CBV Comparison

Feature / Criterion Function-Based View (FBV) Class-Based View (CBV)
Implementation Pure Python function Python class inheriting from View
HTTP Method Routing Manual if/elif request.method == ... Automatic dispatching to get(), post(), etc.
Code Reuse Achieved via helper functions or decorators Achieved via inheritance, mixins, and generic views
Readability & Simplicity Explicit, straightforward control flow; easy to read Abstracted, modular; requires understanding class hierarchy
Best Use Cases One-off custom views, complex custom workflows, simple endpoints CRUD operations, repetitive models, REST APIs, reusable logic
